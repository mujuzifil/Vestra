# VESTRA Commerce Platform — Production Deployment Recovery Report

## Executive Summary

The VESTRA Commerce Platform has been successfully deployed to production and all three public endpoints are now live over valid HTTPS:

- **Website:** https://vestradetergents.com
- **API:** https://api.vestradetergents.com
- **Admin Portal:** https://admin.vestradetergents.com

The deployment recovered from a set of infrastructure and container issues that prevented the Docker Compose stack from starting cleanly. All identified blockers have been resolved with permanent engineering fixes committed to the `develop` branch and merged into `master` as release `v1.0.0`.

## Root Causes Discovered

### 1. Nginx bootstrap configuration not loaded
**Symptom:** `vestra-nginx` started but did not bind to port 80, so ACME HTTP-01 challenges could not be served.

**Cause:** `nginx/nginx.conf` used `include /etc/nginx/conf.d/vestra*.conf;`, which only matched the rendered SSL vhost. The bootstrap `default.conf` was ignored, leaving nginx with no listen sockets after the SSL vhost was removed.

**Fix:** Changed the include glob to `include /etc/nginx/conf.d/*.conf;` so the HTTP bootstrap config loads first.

### 2. Duplicate `default_server` after SSL rendering
**Symptom:** `nginx -t` failed with `a duplicate default server for 0.0.0.0:80` after certificates were provisioned.

**Cause:** Both `conf.d/default.conf` (bootstrap) and `conf.d/vestra.conf` (SSL template) declared `listen 80 default_server;`.

**Fix:** Updated `scripts/render-nginx.sh` to remove `default.conf` before rendering the full SSL vhost.

### 3. Frontend health probe missing HTTP client
**Symptom:** `vestra-frontend` never reached healthy status.

**Cause:** The Dockerfile and Compose health check used `wget`, but `node:22-bookworm-slim` does not include `wget` or `curl`.

**Fix:** Installed `curl` in the frontend runtime stage and switched both the Dockerfile `HEALTHCHECK` and `docker-compose.prod.yml` health check to use `curl -fsS`.

### 4. Deployment helper scripts not executable
**Symptom:** `./scripts/init-certs.sh: Permission denied` during deploy.

**Cause:** `init-certs.sh` and `render-nginx.sh` were committed without the executable bit.

**Fix:** `chmod +x` applied to both scripts and committed.

### 5. Missing SSL certificate for admin domain
**Symptom:** Nginx startup failed because `admin.vestradetergents.com` certificate did not exist.

**Cause:** The admin domain was added to `.env.production` but a certificate had never been issued.

**Fix:** The `scripts/init-certs.sh` bootstrap flow successfully issued a new Let's Encrypt certificate for `admin.vestradetergents.com`.

### 6. Git push unavailable from production server
**Symptom:** `git push origin develop` failed with `could not read Username for 'https://github.com'`.

**Cause:** Repository origin is HTTPS and no GitHub credentials are stored on the server.

**Resolution status:** An SSH deploy key has been generated at `/home/deploy/.ssh/github_deploy`. The public key must be added to the GitHub repository (or to a user account) before the server can push.

## Remaining Risks

1. **Git synchronization:** `master` and `v1.0.0` tag are only on the production server. Until the deploy SSH key is added to GitHub, the remote repository is out of sync.
2. **Frontend image size:** Installing `curl` and its dependencies increases the frontend image slightly. Consider a smaller HTTP probe (e.g., a static Node script) in a future iteration.
3. **Nginx bootstrap race:** If `default.conf` is ever re-created after SSL rendering (e.g., by recreating the nginx container without running `render-nginx.sh`), nginx will fail to start. The deploy script handles this on normal deploys, but manual container recreation should be followed by `render-nginx.sh`.
4. **Certificate expiry monitoring:** Let's Encrypt expiry is ~90 days. Renewal is handled by the certbot container, but monitoring/alerting should be added.

## Additional Post-Deployment Fixes (2026-07-25)

After the initial deployment, the admin portal login flow and dashboard required further fixes before the deployment could be considered complete.

### 7. Admin login returned 403 after authentication

**Symptom:** Submitting valid credentials on `https://admin.vestradetergents.com/login` returned HTTP 403.

**Cause:** `App\Models\User` did not implement `Filament\Models\Contracts\FilamentUser`. Filament's `Authenticate` middleware therefore denied every request to the admin panel, including the post-login redirect.

**Fix:**
- Implemented `FilamentUser` on `App\Models\User`.
- Added `canAccessPanel(Panel $panel): bool` returning `$this->isAdmin()`.
- Removed the ineffective `CustomLoginResponse` workaround file and binding.

**File:** `backend/app/Models/User.php`

### 8. Filament resources missing `getPages()`

**Symptom:** Filament routes for some admin resources (e.g., Notification Delivery, Orders) were not registered, causing 404s / route lookup failures inside the panel.

**Cause:** `NotificationDeliveryResource` lacked `getPages()` entirely, and `OrderResource` had its page classes but the `getPages()` method was missing.

**Fix:**
- Added `getPages()` to `NotificationDeliveryResource` and created the corresponding `Pages/ListNotificationDeliveries` class.
- Added `getPages()` to `OrderResource` referencing the existing `EditOrder`, `ListOrders`, and `ViewOrder` page classes.

**Files:**
- `backend/app/Filament/Resources/NotificationDeliveryResource.php`
- `backend/app/Filament/Resources/NotificationDeliveryResource/Pages/ListNotificationDeliveries.php`
- `backend/app/Filament/Resources/OrderResource.php`

### 9. Admin dashboard crashed with HTTP 500

**Symptom:** After forced password change, the admin dashboard rendered HTTP 500.

**Cause:** `ApiAnalyticsService::errorRate()` accessed `$rows[$dateKey]` directly on a Laravel Collection. When no API request logs existed for a given date, the missing key threw `Undefined array key "2026-07-25"` inside the `ApiHealthWidget` on the dashboard.

**Fix:** Changed the access to `$rows->get($dateKey)`, returning `null` for missing dates. The existing null-safe operator then correctly defaults to zero.

**File:** `backend/app/Services/ApiAnalyticsService.php`

## Additional Post-Deployment Fix — Notifications Page (2026-07-25)

After the initial go-live, authenticated customers visiting `https://vestradetergents.com/notifications` were shown the generic "Something went wrong" error page instead of their notifications.

### Symptom

- `/notifications` rendered the error boundary.
- Laravel logs showed `401 Unauthorized` from `/api/v1/notifications` during Next.js static generation.
- The API response shape for paginated notifications was missing `current_page`, `last_page`, etc.
- A React hydration mismatch (#418) was thrown by the notification badge and the authenticated page shell.

### Root causes

1. **SSR unauthenticated fetch**
   - `useNotifications` and `useUnreadNotifications` executed during Next.js static prerender, where `localStorage` has no auth token.
   - The API returned 401, `handleResponse` threw `ApiRequestError`, and the error boundary rendered the generic failure page.

2. **Pagination metadata lost**
   - `NotificationController::index()` and `::unread()` passed `NotificationResource::collection($paginator)` directly into `successResponse()`, which serialised the paginator through `json_encode` and flattened the wrapper.
   - The API returned `"data": [...]` instead of the expected paginator object, so the frontend could not compute `hasMore`.

3. **Null-safety crash**
   - `notifications-page-client.tsx` used `data?.notifications.some(...)`.
   - When the query errored, `data` was `undefined`, so `data?.notifications` was `undefined` and `.some()` threw.

4. **Notification bell hydration mismatch**
   - `NotificationBell` rendered the unread badge during SSR with count `0`, then the client fetched a non-zero count, causing React hydration error #418.

5. **Authenticated-page hydration mismatch**
   - On the server, the notifications page rendered the "No notifications" empty state (auth token is absent during SSR).
   - On the client, the auth context read the token from `localStorage` and rendered the loading spinner while fetching the profile.
   - The mismatch produced an additional React hydration error.

### Fixes

1. Disabled both notification queries during SSR:
   - `enabled: typeof window !== "undefined"` in `frontend/hooks/use-notifications.ts`.

2. Preserved paginator metadata in the API:
   - `backend/app/Http/Controllers/Api/V1/NotificationController.php` now calls `->response()->getData(true)` and returns `data`, `current_page`, `last_page`, `per_page`, and `total`.

3. Made the page null-safe:
   - `notifications-page-client.tsx` uses `data?.notifications?.some(...)`.

4. Guarded the notification bell with a mount effect:
   - `frontend/components/notifications/notification-bell.tsx` only renders the badge after `useEffect(() => setMounted(true), [])`.

5. Guarded the authenticated notifications page with a mount effect:
   - `frontend/app/notifications/notifications-page-client.tsx` returns `null` until the client has mounted, ensuring identical SSR and hydration output.

### Files modified

- `frontend/hooks/use-notifications.ts`
- `frontend/components/notifications/notification-bell.tsx`
- `frontend/app/notifications/notifications-page-client.tsx`
- `backend/app/Http/Controllers/Api/V1/NotificationController.php`

## Additional Post-Deployment Fix — Product Listing (2026-07-25)

After go-live, the storefront product catalogue at `https://vestradetergents.com/products` displayed "No products found" even though product detail pages (e.g. `/products/heavy-duty-detergent`) loaded correctly and the database contained active products.

### Symptom

- `/products` showed the empty state.
- Product detail pages worked.
- The API `/products` endpoint returned HTTP 200 with product data.
- No Laravel exceptions were logged.

### Root cause

`ProductController::index()` returned `ProductResource::collection($products)` directly into `successResponse()`. Serialising a Laravel `ResourceCollection` paginator through the wrapper's `json_encode` flattened the paginator structure. The API returned:

```json
{ "success": true, "data": [ ... products ... ] }
```

The frontend expected the standard Laravel paginator shape:

```json
{ "success": true, "data": { "data": [ ... ], "meta": { ... } } }
```

Because `searchResult?.data` was an array instead of an object, `products = searchResult?.data ?? []` evaluated to an empty array and the grid never rendered.

### Fix

`backend/app/Http/Controllers/Api/V1/ProductController.php` now serialises the resource collection through `->response()->getData(true)` before wrapping it in `successResponse()`, preserving the `data` / `links` / `meta` paginator structure.

## Commerce Flow Remediation

After the product-listing fix, two critical defects remained in the customer purchasing journey:

1. Product images were missing from the shopping cart, checkout order summary, order confirmation, and order detail pages.
2. Placing an order failed with a generic "Failed to fetch" / HTTP 500 error.

### Defect 1 — Missing product images in order summaries

**Symptom**

- Cart page, checkout review step, checkout confirmation (`/checkout/confirm`), and account order detail (`/account/orders/[id]`) showed the placeholder image for every item.
- Product detail pages rendered images correctly, proving storage and media URLs were fine.

**Root cause**

The backend did not eager-load product images for cart and order items, and `OrderItemResource` did not expose the related `product` at all. The frontend components for order confirmation and order detail were also hard-coded to `/assets/images/products/placeholder.png`.

**Fix**

| File | Change |
|------|--------|
| `backend/app/Repositories/CartRepository.php` | `Cart::with(["items.product"])` → `Cart::with(["items.product.images"])` |
| `backend/app/Services/OrderService.php` | Eager-load `items.product.images` on cart reads, created orders, user order listings, and single-order lookups |
| `backend/app/Services/DistributorOrderService.php` | Eager-load `items.product.images` on cart reads, created orders, distributor order listings, and lookups |
| `backend/app/Http/Resources/V1/OrderItemResource.php` | Added `product => new ProductResource($this->whenLoaded("product"))` so the frontend can access images |
| `frontend/app/checkout/confirm/confirm-page-client.tsx` | Use `item.product?.images?.[0]?.image` with placeholder fallback |
| `frontend/app/account/orders/[id]/order-detail-client.tsx` | Use `item.product?.images?.[0]?.image` with placeholder fallback |
| `frontend/app/distributor/orders/[id]/order-detail-client.tsx` | Use `item.product?.images?.[0]?.image` with placeholder fallback |
| `frontend/types/index.ts` | Added optional `product?: Product` to `OrderItem` interface |

### Defect 2 — Order placement failed with HTTP 500

**Symptom**

Clicking **Place Order & Continue to Payment** returned "Something went wrong" / "Failed to fetch" for every payment method.

**Root cause**

Two independent fatal errors occurred during checkout:

1. `App\Mail\TemplateMailable` declared a typed promoted property `public array $metadata`, which collides with Laravel 12's inherited untyped `Illuminate\Mail\Mailable::$metadata`. PHP raised: `Type of App\Mail\TemplateMailable::$metadata must not be defined (as in class Illuminate\Mail\Mailable)`.
2. `NotificationDispatcherService::sendInApp()` referenced an undefined `$variables` variable. Because in-app notifications are dispatched after order creation, this caused a second fatal error once the mail error was bypassed.

**Fix**

| File | Change |
|------|--------|
| `backend/app/Mail/TemplateMailable.php` | Replaced the typed promoted property with a plain constructor argument `$metadata` and assigned it to `$this->metadata` |
| `backend/app/Services/NotificationDispatcherService.php` | Added `array $variables` to `sendInApp()` and passed `$variables` from the `match` arm in `dispatch()` |
