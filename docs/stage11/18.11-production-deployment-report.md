# VESTRA Commerce Platform — Production Deployment Recovery Report

## Executive Summary

The VESTRA Commerce Platform has been successfully deployed to production and all three public endpoints are now live over valid HTTPS:

- **Website:** https://vestradetergents.com
- **API:** https://api.vestradetergents.com
- **Admin Portal:** https://admin.vestradetergents.com

The deployment recovered from a set of infrastructure and container issues that prevented the Docker Compose stack from starting cleanly. All identified blockers have been resolved with permanent engineering fixes committed to the `develop` branch and merged into `master` as release `v1.0.0`.

---

## Root Causes Discovered

### 1. Nginx bootstrap configuration not loaded
**Symptom:** `vestra-nginx` started but did not bind to port 80, so ACME HTTP-01 challenges could not be served.

**Cause:** `nginx/nginx.conf` used `include /etc/nginx/conf.d/vestra*.conf;`, which only matched the rendered SSL vhost. The bootstrap `default.conf` was ignored, leaving nginx with no listen sockets after the SSL vhost was removed.

**Fix:** Changed the include glob to `include /etc/nginx/conf.d/*.conf;` so the HTTP bootstrap config loads first.

### 2. Duplicate `default_server` after SSL rendering
**Symptom:** `nginx -t` failed with `a duplicate default server for 0.0.0.0:80` after certificates were provisioned.

**Cause:** Both `conf.d/default.conf` (bootstrap) and `conf.d/vestra.conf` (SSL template) declared `listen 80 default_server;`.

**Fix:** Updated `scripts/render-nginx.sh` to remove `default.conf` before rendering the full SSL vhost.

### 3. Frontend health probe missing HTTP client
**Symptom:** `vestra-frontend` never reached healthy status.

**Cause:** The Dockerfile and Compose health check used `wget`, but `node:22-bookworm-slim` does not include `wget` or `curl`.

**Fix:** Installed `curl` in the frontend runtime stage and switched both the Dockerfile `HEALTHCHECK` and `docker-compose.prod.yml` health check to use `curl -fsS`.

### 4. Deployment helper scripts not executable
**Symptom:** `./scripts/init-certs.sh: Permission denied` during deploy.

**Cause:** `init-certs.sh` and `render-nginx.sh` were committed without the executable bit.

**Fix:** `chmod +x` applied to both scripts and committed.

### 5. Missing SSL certificate for admin domain
**Symptom:** Nginx startup failed because `admin.vestradetergents.com` certificate did not exist.

**Cause:** The admin domain was added to `.env.production` but a certificate had never been issued.

**Fix:** The `scripts/init-certs.sh` bootstrap flow successfully issued a new Let's Encrypt certificate for `admin.vestradetergents.com`.

### 6. Git push unavailable from production server
**Symptom:** `git push origin develop` failed with `could not read Username for 'https://github.com'`.

**Cause:** Repository origin is HTTPS and no GitHub credentials are stored on the server.

**Resolution status:** An SSH deploy key has been generated at `/home/deploy/.ssh/github_deploy`. The public key must be added to the GitHub repository (or to a user account) before the server can push.

## Remaining Risks

1. **Git synchronization:** `master` and `v1.0.0` tag are only on the production server. Until the deploy SSH key is added to GitHub, the remote repository is out of sync.
2. **Frontend image size:** Installing `curl` and its dependencies increases the frontend image slightly. Consider a smaller HTTP probe (e.g., a static Node script) in a future iteration.
3. **Nginx bootstrap race:** If `default.conf` is ever re-created after SSL rendering (e.g., by recreating the nginx container without running `render-nginx.sh`), nginx will fail to start. The deploy script handles this on normal deploys, but manual container recreation should be followed by `render-nginx.sh`.
4. **Certificate expiry monitoring:** Let's Encrypt expiry is ~90 days. Renewal is handled by the certbot container, but monitoring/alerting should be added.

## Recommendations

1. **Add the deploy SSH key to GitHub** using the public key below, then run `git push origin master develop --tags` from `/opt/vestra`.
2. **Set up uptime monitoring** for the three HTTPS endpoints and alert on non-200 responses.
3. **Add certificate expiry alerts** at 30, 14, and 7 days before expiry.
4. **Run backend feature tests** (`php artisan test`) during the next maintenance window to confirm no regressions from the stage 18.11 work.
5. **Review CI/CD** to ensure the deployment scripts are executable and the frontend Dockerfile includes `curl` before the next automated build.
6. **Consider splitting build and deploy** in CI so images are built once and tagged, rather than rebuilt on the production host.
